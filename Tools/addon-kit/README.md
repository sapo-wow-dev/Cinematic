# Addon kit

Testing Cinematic against other addons from what Cinematic itself touches,
not only from what each addon makes. Plan: [../addon-kit-plan.md](../addon-kit-plan.md).

## Built (step 1, 2026-11-25)

| File | What |
|---|---|
| `touchpoints.py` | Every game frame and game global our code touches, with its files, what's done to it and the settings that reach it. Checks the code against `touchpoints.txt`; `--update` saves it. In prerelease. |
| `touchpoints.txt` | The registry (generated, never edited by hand). |
| `touchmap.lua` | The settings sweep on the stand-in game in touch mode (`Tools/offline/wow.lua`, `M.StartTouches`): what each setting change reaches. `touchpoints.py` runs it on both clients. |
| `misses.py` + `misses/*.txt` | Every other-addon bug that reached players, as an offline case. Each test must FAIL on the code before its fix and pass now. In prerelease. |

## Built (step 2, 2026-11-25)

| File | What |
|---|---|
| `rulewalk.lua` | Every row's show logic through the real path that decides what fades (`ns.CombatShownFrames`, `ns.RowOnNow`), with the rule facts forced. It reads `ns.RULE_WORDS`, `ns.COMBAT_SHOW` and `ns.ROW_FALLBACK` as the code has them, so new words and rows join without anyone listing them. |
| `rulewalk.py` | Runs it on both clients. `--update` saves the baselines; `--selftest` runs five mutants, each a deliberate break in the rule code, and the walk must FAIL on each. In prerelease. |
| `rulewalk-<client>.txt` | Each row's ticks in each state, plus what the rows that follow another do. Generated by `--update`. |

What the walk checks:
1. **Words:** every word and alias compiles and reads its own fact, `not` reads the other way, `and`/`or` behave as they say, and each fact's own word reads that fact.
2. **Facts:** every word's fact is worked out (a new word with nothing setting its fact FAILs), and every fact worked out has a word reading it.
3. **Rows:** each of about 250 Standard Frames and other-addon rows, with each word as its rule, shows with the fact true and hides with it false (`not`: the reverse).
4. **Grid rows:** the same through `ns.RowOnNow`.
5. **Follow:** a row set to follow another takes its rule and its ticks, and gets its own back once unset.
6. **Ticks:** each row × each tick column × calm, fight (CineMode staying or not), enemy target and friendly target, compared with the baseline. Rows that follow another's ticks until set are included.

One gap: the grid rows' keys come from the rows above plus the ones the code names directly. Keys built from tables (chat types, effects) are reached only through `RowOnNow`'s shared logic. Step 4's probes cover their wiring.

## Built (step 3, 2026-11-25)

| File | What |
|---|---|
| `../../Dev/AddonKit.lua` | The probe registry and runner (dev copy). `ns.AddonKit.Probe{ id, v, touches, settings, run }`. A probe records fields and never judges. `ns.AddonKit.Run(label)` writes `CinematicDB.addonKitLog`: an `H` header line (format, client, build, loaded addons), `R probe field value v`, `E probe error`, then `D`. |
| `../../Dev/AddonKitProbes.lua` | The probes. The first is `chat.linesOnly`, the 2979131 miss. Step 4 adds the rest. |
| `ns.AddonKitExpect` (AddonSupport.lua) | In a Support file: with this addon loaded, this probe's field is meant to differ, and why. Literal strings only, since `diff.py` reads them from the file text. |
| `kitrun.lua` | The probes run offline on the stand-in, writing the same lines, optionally with addons said to be loaded. |
| `diff.py` | `baseline <client>` saves a run with no other addon to `baseline-<client>.txt`. `check <Addon> <client>` compares a solo run with that baseline: a difference not declared with `ns.AddonKitExpect` FAILs. Both read the game's saved log, or `--log FILE`. |

`diff.py check` also fails when a run can't be judged:
- a probe errored;
- the baseline is from another game build;
- a probe's `v` changed, or a probe was added or removed, since the baseline;
- the named addon isn't loaded in the run.

A declaration that matched nothing is a note. `touchpoints.py` also fails a probe that names a touch point the code doesn't touch, and reports how many touch points have a probe.

## Built (steps 4, 5 and 7, 2026-11-25)

**Probes for every touch point (step 4).** Most probes are generated when they run, from the code's own lists, so nothing new needs a probe written for it:
- `frame.<row>`: each game frame a Standard Frames row fades. Whether it's there, up and seen, its alpha with CineMode off, its parent, and whether it refuses addon code.
- `touch.<point>`: every touch point in the registry. A frame's state, or a function or table that's still the same object as at login. `Dev/AddonKitTouches.lua` is generated by `touchpoints.py --update`.
- `hook.<target>`: every game function or method we hook, still the one we hooked. An addon that swaps in its own afterwards silently drops our hook.
- `link.<part>`: each frame link part, the game's frame or which addon's.
- `addons.conflicts` and `addons.yields`: "owned" probes. An addon's own rows there count as its own, not as differences.

That's 615 probes, covering all 448 touch points. `unprobed.txt` is kept by hand: a touch point with no probe and no line there FAILs. A difference nobody declared also lists the settings that reach that frame, which are the features to check.

**The in-game test (step 5).** `/cine debug addonkit [Addon ...]` (`Dev/AddonKitTest.lua`). With no names, it runs every installed supported addon. It runs these stages:
1. The baseline, with `/cine debug solo none`.
2. Each addon alone: its probes, then `addontest <Addon> quick` for its rows.
3. Your addon list back.

Each stage waits on one Reload button. Afterwards, `diff.py all <client>` saves the baseline and judges each addon. `Tools/offline/addonkittest.lua` drives the test offline with fake installed addons. It caught two bugs before any game run: slash commands lowercase addon names, and "already alone" was judged by the solo setting rather than by what's loaded.

**The scan (step 7).** Section 3b of `scan_addon.py` lists our features on each game frame the addon touches. The `/addon-support` skill's Phase 1 and Phase 3 use the kit now.

**Steps 6 and 8 run in game**: see `backfill.md`.

```
python -I Tools/addon-kit/diff.py --selftest
python -I Tools/addon-kit/rulewalk.py
python -I Tools/addon-kit/rulewalk.py --selftest
python -I Tools/addon-kit/touchpoints.py
python -I Tools/addon-kit/touchpoints.py --update
python -I Tools/addon-kit/misses.py
```

## When touchpoints.py FAILs

Each FAIL is a change in what another addon can break:
- **new touch point**: our code reaches a game frame it didn't before;
- **newly touched by \<file\>**: another of our files works on that frame;
- **setting \<key\> newly reaches it**: a feature now acts on that frame (as
  `chatPeekLinesOnly` on `ChatFrame#`, the DaylightUI double-line bug).

Run `--update` in the same commit. In step 4, each touch point also gets a
probe, and a FAIL there means writing the probe as well.

## How settings link to frames

Static links come first: the game's names come from the client's
`BlizzardInterfaceCode` export, and only the names are read. A setting links
to a frame in one of three ways:
- the same top-level block reads the setting and names the frame;
- one of the two happens in a small function that the block calls;
- the setting is read in a small feature file (at most 15 frames and 60
  settings) that touches the frame.

The dynamic part, the sweep in touch mode, adds the methods called on each
frame and the hooks on it. Font objects, templates and API calls are touch
points too, but no settings link to them. With no export installed, only
the sweep's touches count, and the run says so.

## Adding a miss

When a player finds an addon bug our support missed:
1. Fix it with an offline test.
2. Add `misses/<addon>-<what>.txt`, giving the fix commit, the test, the
   addon and what players saw.
3. Run `misses.py <name>`. A test that only errors on the old code (no FAIL
   line) can't prove the bug, so the case isn't kept. That's why the
   EllesmereUI chat case (0bd9803) isn't in the corpus.
4. Add the check that would have caught it to the kit.
